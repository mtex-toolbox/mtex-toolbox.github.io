--- title: "EBSD Maps and SEM Images" sidebar: documentation_sidebar permalink: EBSDMapsAndImages.html folder: documentation toc: false --- EBSD Maps and SEM Images edit page

An EBSD map and a forescatter or BSE image of the same area are two rasters of the same piece of specimen. Putting them together needs two questions answered, and they are independent of each other:

  • where on the specimen does each picture sit - its reference frame
  • which way round is each array stored - its layout

The first decides what is drawn where. The second decides what img(i,j) means. This page walks through both on one WC-Co dataset, an EBSD map and four forescatter images of the same 20 x 15 micron area.

{% highlight matlab %} plottingConvention.default('y↓→x'); mtexdata trueEbsdWCCoSmall img = ebsd.opt.trueEbsdImgs; {% endhighlight %} {% highlight plaintext %} ebsd = EBSDsquare (y↓→x, row↓→col) Phase Orientations Mineral Color Symmetry Crystal reference frame 0 89 (0.72%) notIndexed none 1 11180 (91%) W C LightSkyBlue -6m2 X||a*, Y||b, Z||c 2 991 (8.1%) Co-fcc DarkSeaGreen m-3m 3 28 (0.23%) Co-hcp Goldenrod 6/mmm X||a*, Y||b, Z||c Properties: bc, bs, bands, MAD, quality, oldId Scan unit : um X x Y x Z : [10 → 30] x [8 → 23] x [0 → 0] Normal vector: (0,0,1) Square grid :96 x 128 source: trueEbsdWCCo, centre half of the field of view, coarsened 4x madeBy: trueEBSD tools/makeWCCoSmall.m {% endhighlight %}

mapImage is a picture together with the geometry that says where it sits: an origin, a pixel size and the frame those refer to. A channel of an EBSD map joins such a sequence as one entry of it, so a map and its images are one array rather than two different kinds of thing.

{% highlight matlab %} imgList = [mapImage(ebsd.bc,ebsd, 'name','bcImg'), ... mapImage(img.fsdT1, 'dxy',img.pixSzImg, 'name','fsdT1'), ... mapImage(img.fsdT10,'dxy',img.pixSzImg, 'name','fsdT10')] {% endhighlight %} {% highlight plaintext %} imgList = mapImage (y↓→x) image pixel frame layout name EBSD 1 96 x 128 0.16 um y↓→x row↓→col bcImg W C, Co-fcc, Co-hcp 2 192 x 256 0.08 um iY↓→iX row↓→col fsdT1 - 3 192 x 256 0.08 um iY↓→iX row↓→col fsdT10 - {% endhighlight %}

Plotting the sequence draws each entry where it sits, one axis per picture

{% highlight matlab %} plot(imgList,'layout',[1,3],'refFrame','on') {% endhighlight %}
{% include inline_image.html file="EBSDMapsAndImages_01.png" %}

What an Image Does Not Know

The map entry brings the map's frame along, so it knows the specimen

{% highlight matlab %} imgList(1).frame {% endhighlight %} {% highlight plaintext %} ans = specimenFrame (specimen, y↓→x) {% endhighlight %}

An image does not. Which specimen direction its x runs along is not in the array and cannot be computed from it - somebody has to say. Until they do, MTEX gives the image a frame of its own rather than assuming the map's, and names its axes iX, iY, iZ so that every plot and every display shows they are the image's own

{% highlight matlab %} imgList(2).frame {% endhighlight %} {% highlight plaintext %} ans = specimenFrame (image, iY↓→iX) {% endhighlight %}

Two Pictures That Disagree

Here everything was collected in one session, which is why the plots above agree. To get the other case, turn the map through 90 degree - what a stage rotation between the two acquisitions would leave you with.

{% highlight matlab %} ebsd = rotate(ebsd,90*degree); imgList = [mapImage(ebsd.bc, ebsd, 'name', 'bcImg'), ... mapImage(img.fsdT1, 'dxy', img.pixSzImg, 'name', 'fsdT1'), ... mapImage(img.fsdT10,'dxy', img.pixSzImg, 'name', 'fsdT10')] {% endhighlight %} {% highlight plaintext %} imgList = mapImage (y↓→x) image pixel frame layout name EBSD 1 128 x 96 0.16 um y↓→x row↓→col bcImg W C, Co-fcc, Co-hcp 2 192 x 256 0.08 um iY↓→iX row↓→col fsdT1 - 3 192 x 256 0.08 um iY↓→iX row↓→col fsdT10 - {% endhighlight %}

The map's array is 128 x 96 now where the pictures are 192 x 256 - the two are transposed to each other. Plotting shows it at once: the map is on its side relative to the images, and somewhere else on the specimen

{% highlight matlab %} plot(imgList,'layout',[1,3],'refFrame','on') {% endhighlight %}
{% include inline_image.html file="EBSDMapsAndImages_02.png" %}

Saying Which Way Round the Map Is

Each entry is drawn the way its own frame says it should be, so changing the map's frame changes what you see. Turn it until the plots agree with each other; here the map needs 'x↑→y' and the images keep the default.

This is the part only you can supply. It is a fact about how the data was collected, and no amount of looking at the numbers will recover it.

{% highlight matlab %} ebsdFrame = imgList(1).frame; ebsdFrame.how2plot = 'x↑→y'; plot(imgList,'layout',[1,3]) {% endhighlight %}
{% include inline_image.html file="EBSDMapsAndImages_03.png" %}

All three now agree on screen, and that is a statement about the specimen: byScreenAlignment means exactly I have plotted these and they are the same way up. transformReferenceFrame takes that statement and restates every entry in one frame

{% highlight matlab %} imgList = transformReferenceFrame(imgList,ebsdFrame,'byScreenAlignment') {% endhighlight %} {% highlight plaintext %} imgList = mapImage (x↑→y) image pixel frame layout name EBSD 1 96 x 128 0.16 um x↑→y row↓→col bcImg W C, Co-fcc, Co-hcp 2 192 x 256 0.08 um x↑→y row↓→col fsdT1 - 3 192 x 256 0.08 um x↑→y row↓→col fsdT10 - {% endhighlight %} {% highlight matlab %} plot(imgList,'layout',[1,3]) {% endhighlight %}
{% include inline_image.html file="EBSDMapsAndImages_04.png" %}

How the Array Is Stored

Look at the layout column above. It changed too, and so did the shape of the map - a 128 x 96 array came back 96 x 128. That is the second question, and it has nothing to do with the specimen: it is the order the numbers sit in memory.

The layout is a gridLayout, and there is nothing more to it than two directions - the one the row index advances along, and the one the column index advances along, in that order

{% highlight matlab %} imgList(1).layout {% endhighlight %} {% highlight plaintext %} ans = gridLayout (row||-x, col||y) {% endhighlight %}

Every mapImage states its own, and so does a gridded map

{% highlight matlab %} ebsd.layout {% endhighlight %} {% highlight plaintext %} ans = gridLayout (row||y, col||x) {% endhighlight %}

Putting a Map in an Image's Layout

gridify takes such a layout, which is how a map is put in the same order as a picture it is to be compared with. 'columnMajor' and 'rowMajor' are the two it knows by name - see Square and Hex Grids - and any other is stated as a gridLayout. Start again from the map as it was imported, and say the detector had been mounted a quarter turn from the scan, so its rows run against x and its columns along y

{% highlight matlab %} mtexdata trueEbsdWCCoSmall silent gL = gridLayout(-xvector,yvector) {% endhighlight %} {% highlight plaintext %} gL = gridLayout (row||-x, col||y) {% endhighlight %}

Then the map goes into that layout and its shape follows

{% highlight matlab %} ebsdI = gridify(ebsd,gL) {% endhighlight %} {% highlight plaintext %} ebsdI = EBSDsquare (y↓→x, row←col↓) Phase Orientations Mineral Color Symmetry Crystal reference frame 0 89 (0.72%) notIndexed none 1 11180 (91%) W C LightSkyBlue -6m2 X||a*, Y||b, Z||c 2 991 (8.1%) Co-fcc DarkSeaGreen m-3m 3 28 (0.23%) Co-hcp Goldenrod 6/mmm X||a*, Y||b, Z||c Properties: bc, bs, bands, MAD, quality, oldId Scan unit : um X x Y x Z : [10 → 30] x [8 → 23] x [0 → 0] Normal vector: (0,0,1) Square grid :128 x 96 source: trueEbsdWCCo, centre half of the field of view, coarsened 4x madeBy: trueEBSD tools/makeWCCoSmall.m {% endhighlight %}

Nothing was resampled and no value invented - a transpose and two flips are all that is ever applied, which is why this is safe to do to orientation data. For this particular pair of layouts it is a quarter turn, and it really is only that

{% highlight matlab %} isequal(ebsdI.bc, rot90(ebsd.bc)) {% endhighlight %} {% highlight plaintext %} ans = logical 1 {% endhighlight %}

so putting it back is exact

{% highlight matlab %} isequal(gridify(ebsdI,ebsd.layout).bc, ebsd.bc) {% endhighlight %} {% highlight plaintext %} ans = logical 1 {% endhighlight %}

Note what has not changed. The layout is how the measurements are stored, not where the specimen is, so the map still plots the same way up - MTEX moves the camera for the screen, never the data

{% highlight matlab %} plot(ebsd,ebsd.bc,'micronbar','off','layout',[1,2]), mtexColorMap gray title('as imported') nextAxis plot(ebsdI,ebsdI.bc,'micronbar','off'), mtexColorMap gray title('row ||-x, col ||y') {% endhighlight %}

Comparing Them Pixel by Pixel

Once the frames agree and the layouts agree, the two rasters are ordinary matrices of the same thing and may be handed to any image processing tool side by side. What is still missing is a common pixel grid: the map here is on 0.159 micron and the images on 0.0795.

interp resamples an image at any positions, so the map's own are all it takes. The image has no origin of its own - that was the first question again - so state where its first pixel sits.

{% highlight matlab %} mgI = mapImage(img.fsdT1,'dxy',img.pixSzImg,'origin',ebsd.pos(1,1)); ebsd.prop.fsdT1 = interp(mgI,ebsd.pos); {% endhighlight %}

From here the image is just another property of the map, and travels with it through cropping, gridding and indexing

{% highlight matlab %} plot(ebsd,ebsd.fsdT1) mtexColorMap gray {% endhighlight %}
{% include inline_image.html file="EBSDMapsAndImages_06.png" %}

The two still do not overlay perfectly: the beam drifts during a scan, the camera moves between acquisitions, the specimen is tilted. Each of those is a spatial transform that can be fitted from the two pictures and taken back out, which is what TrueEBSD does - and it starts exactly here, with a sequence whose entries agree about the specimen and about the order they are stored in.

See also Square and Hex Grids for what a layout is good for, and Reference Frame Alignment for the other frame question a map raises - whether its Euler angles and its coordinates refer to the same axes.
